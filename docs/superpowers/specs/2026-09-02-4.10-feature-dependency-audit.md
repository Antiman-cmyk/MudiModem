# MudiModem 1.7.0 → GL 4.10.0 — feature-by-feature dependency audit

**Method (2026-09-02, second pass):** every user-facing feature and daemon of MudiModem was
taken in turn; its complete dependency set was extracted from the code by grep (ubus
object+method, GL RPC object+method, ws socket, sysfs/dev/proc/etc path, spawned process,
GL init script, opkg package); each dependency was then checked against the extracted
4.10.0 image. This complements (and corrects) the subsystem-oriented first pass and the
merged plan `docs/superpowers/plans/2026-09-02-firmware-4.10-migration-plan.md`.

Legend: ✅ unchanged in 4.10 (verified in image) · ⚠️ changed — action required · ❌ broken
on 4.10 · 🔴 cannot be settled offline — Phase 0 on-box item · 🔵 reported from a live
4.10 unit (EU) not yet captured here.

## Net-new findings from this pass (not in the first pass or Plan B)
1. **`pkill` does not exist in the 4.10 busybox** → `set_lcd`'s SIGHUP live-reload is a silent no-op; replace with `pgrep`+`kill`.
2. **Challenge-response login is NOT a 4.10 change** — `oui-rpc.lua` is identical to the 4.8 reference copy; plan §1 wording corrected.
3. `gl.conf` is functionally identical (static `.js/.json` serving, `/cgi-bin/` fastcgi, `/rpc`, `/ws`) — no packaging risk from nginx config.
4. All LCD renderer inputs except the backlight node name and fb0 size are present unchanged (`iwinfo`, `gl-clients`, `mcu status` fields, GL font files).
5. Speedtest's `proto == "rmnet"` iface selection remains valid in principle (`rmnet.sh` shipped); device name to confirm.
6. `mudi.py`'s LCD-side band writes use `sub_id = slot` — a pre-existing inconsistency with the backend's PLMN-resolved sub_id that the 4.10 band-API rewrite should retire (route LCD band actions through the backend or drop them).
7. `verify.sh` step 8e is guaranteed to fail on 4.10 (no `gl_modem` process) — a red-herring failure to remove first.
